## 5. Hardcoded values (HC) and how to manage them
Reviewers inventoried 18 backend categories, 12 dashboard categories and 9 Android categories. The recurring shapes:
- **Tenant behaviour wired by UUID/name** — 31 UUID literals in 13 dashboard files and ~140 gate call sites; Tata, BMW, PASA, Rajkamal, ByteBack, PMC, MoiSoi, Kinematic, Horizon are all special-cased in code.
- **Identity by string** — platform operator e-mails (now `CROSS_ORG_SUPERADMIN_EMAILS`, defaulting to a list in code), staff domains, display names.
- **Endpoints and limits** — API base URL in 15 iOS files / Android constants, rate limits, role sets duplicated ~12 times, lead-status lists in 15 places.
- **Fixed org** — `candidates.controller.ts` uses one org UUID for every tenant.

**Proposal — one managed configuration layer, three tiers**
1. *Per-tenant feature/behaviour flags* in a `tenant_config` table (org/client/project scope, typed key, JSON value, audit trail) with an admin screen in Client Management; replaces the UUID checks. Resolved once per request and cached 60 s.
2. *Platform settings* (operator list, staff domains, limits, kill-switches) in the same table at `scope = platform`, editable only by operators; env vars become defaults.
3. *Secrets* only in AWS Secrets Manager, injected by reference; never in tables or source. Add gitleaks + GitHub push protection.
Migration path: add the table and a `getConfig(key, scope)` helper, convert one tenant gate at a time (start with Rajkamal's), delete the literal when its last use is gone.

## 6. Performance and load
- **Production, last 3 days (CloudWatch):** 40,489 requests in total (peak 5-minute window ≈ 1.3 req/s), CPU average 0.6 % (peak sample 32 %), memory ≤ 17 %, 22 target 5xx. The API is hugely over-provisioned for its traffic — **no vertical scaling is needed**.
- **The real problem is tail latency:** p99 spikes to 13–16 s *every day at ≈03:27 UTC (08:57 IST, the morning check-in window)* and once to 31 s. That coincides with the in-process daily jobs (daily briefing etc.) running on the same 0.25 vCPU task as user traffic, and there is no timeout on any upstream call (PERF-2). Fix: run the schedulers in a separate worker task (BUG-6), add 20–25 s timeouts to the PostgREST client, and stagger hour-gated jobs.
- **Local load test** (real Express app, fake instant PostgREST with 3 ms latency, 4 vCPU sandbox, demo-fixture endpoints so mostly framework cost): `/health` ≈ 2,700 req/s (p99 55 ms); typical JSON endpoints ≈ 1,500–1,900 req/s (p99 ≈ 60 ms at 64 connections; p99 296 ms at 256). Real handlers are bounded by PostgREST/DB time, not Node.
- **Database:** the unsent-notifications poll was the largest avoidable cost (fixed). Next: PERF-1 (analytics pull up to 100,000 rows into Node, 61 sites — move to SQL aggregates), PERF-4 (`work_activity`/`audit_log` growth and heartbeat writes — partition + retention), enable `pg_stat_statements` (needs a reboot).
- **Single points of failure:** one backend task, one RDS instance hosting both tenants' databases, one PostgREST/GoTrue/storage task per tenant sharing 0.25 vCPU. Recommend 2 backend tasks (after the worker split), Multi-AZ RDS, and ≥ 1 vCPU for the auth stack.
- **Found while measuring:** `cron/leave-carry-forward` and `cron/rescore-planogram-compliance` have no scheduler on AWS; a recurring `unauthorized_client` error every 10 minutes in the backend log (a provider token refresh failing — not investigated).
